# Audit: the spark Discord bot (`bot/**`) against R1–R4

Branch `ldb-arch-review` @ a695bc57c, 2026-09-12. Read-only; `cd bot && npm ci && npm test` was run (the suite fetches read-only from akl.gg by design, see §G). Requirements ranked by the owner: correctness > simplicity > latency (~1 s) > cost.

**One-line verdict:** the bot already *is* the "full in-memory replica fed by the change feed" design, and that half is sound. The over-built half is everything around *stats*: the site-harvest reuse (provenance proof + publish sandwich), the alerting stack, and a `rank` that still says "Computing". Keep the topology; delete the provenance layer in favour of a content-keyed, volume-persisted cell cache with eager compute; fix one real write-misreport hazard.

## A. Runtime topology

- **Where:** one Fly machine, app `spark-bot`, region iad, `shared-cpu-1x`, **1 GB** RAM (`bot/fly.toml:11,31,41`), one 1 GB-class volume at `/data` (`fly.toml:28`). No `[http_service]` (`fly.toml:43`): the process holds an outbound Discord gateway WebSocket only. The stats service is a *separate* Fly app `aklgg-stats-preview`, `shared-cpu-2x`/2 GB (`stats/fly.toml`), Python + Go CLI (`scripts/stats_service/*.py`, 2 685 LOC); the bot does not read its output (no `pointer`/`DATA_LINE` reference anywhere in `bot/src`).
- **Image:** two-stage `node:24-slim`; esbuild bundles `@akl/core` (web/src/core+copy) and `@akl/layout-formats` (db/formats) into `dist/` (`bot/Dockerfile:1-38`). Runtime = `dist/` + prod `node_modules` + two font files. Nothing data-shaped is baked in: wasm, defs, harvests, magic rules all come from `https://akl.gg/data/` at run time (`fly.toml:15`, `Dockerfile:1-4`). Node runs with `--max-old-space-size=192 --max-semi-space-size=8` (`Dockerfile:66`, mirrored `fly.toml:53`).
- **Boot (`bot/src/main.ts:373-458`):** in parallel, (1) `GET /v1/dump/latest.json` → gzip dump → fold every live layout + `spark/1` payload + likes + authors + admins into `Store` (`cache/boot.ts:141-153`, `applyDump` 88-136); (2) `defs.json` + `build_id.json` from the site (`engine/site.ts:70-78`); (3) `prefs.json` from the volume. Then wasm worker boot with pin check (`engine/host.ts:184-192`, throws `EngineSkew` on mismatch → process exits → Fly restarts); then the publish tracker loads `layouts_keys.json`, `layouts.json`, `magic_rules.json`, `build_manifest.json` (~8 MB, `cache/provenance.ts:211-227`, awaited at `main.ts:427`). Harvest tables (~5.4 MB each) and n-gram/extended tables are **lazy** on first use (`engine/site.ts:168-180`). `ensureFresh()` is *not* run before `client.login()` (`main.ts:692`), so the first command pays the dump→head catch-up (§B).
- **Memory:** README-measured idle after boot **188 MB** post-X5b, worst-case 352–412 MB (`bot/README.md:1050-1060`); the Go wasm heap never shrinks and a single engine that has touched heavy extended tables reached 1.1–1.6 GB in the bench (`design/pipeline-313/03-b6-plan.md` §2.2). Memory watchdog DMs at 80 % (`watchdog.ts:87`).
- **Volume state:** only `prefs.json` (per-user corpus/spacegrams/theme, `prefs.ts`) and `spark.pid-marker` (unclean-restart notice, `watchdog.ts:34`). The layout cache and every computed cell are **not** persisted; rebuilt from the dump every boot.
- **Restart/redeploy:** single machine, no queue: messages arriving during boot get no reply, silently. Boot needs akl.gg *and* layoutdb *and* Discord up; any one down → crash loop. Boot cost = dump fetch/parse (~20 MB RSS fold) + wasm (4.6 MB) + 8 MB of proof inputs + gateway login; unmeasured on Fly (the bench measured engine boot alone at 70–78 ms on an M3). Deploys are automatic on every push to `main` touching `bot/**` after the test job (`.github/workflows/bot.yml`).

## B. Command latency path

Every command: gateway → `handleMessage` (`main.ts:221-366`) → synchronous receipt ticket (`:252`, `order.ts:56-91`: a read waits only for earlier *writes*; a write waits for earlier writes) → `ensureFresh()` for every verb except help/search/filter/homerow (`commands/index.ts:81`, `main.ts:289-299`) → verb → reply capped at 2 000 chars with mentions disabled (`main.ts:206-219`).

**`ensureFresh()` (`cache/fresh.ts:122-154`):** one `GET /v1/meta` with `If-None-Match`. The Worker computes the ETag from one D1 query (event head + authors head + import state, `db/src/index.ts:111-132`, `db/src/core/etag.ts`) *before* consulting `caches.default`, and only serves a cached body whose ETag equals the live one (`etag.ts:126-140`), so `Cache-Control: public, max-age=10` (`index.ts:29`) cannot yield a stale 304 (Node's fetch does no HTTP caching). 304 → serve from memory. 200 with `seq > cursor` → `drainChanges` pages `/v1/changes` and does one detail `GET /v1/layouts/{id}?format=spark/1` per changed layout, 8 in flight, applied in seq order (`feed.ts:309-389`). A caller never joins a running check; it waits for one shared follow-up (`fresh.ts:180-199`). Failure → `Error: database unreachable`, never stale data (`main.ts:293-296`). Measured: **43 ms p50 / 63 ms max** for the 304 path; 376 ms first call; ~775 ms 20 events behind (`03-b6-plan.md` §2.4). SSE `/v1/changes/stream` (Worker polls D1 every 2 s, `db/wrangler.toml:25`) folds the same events through the same `applyEvent` as keep-warm (`cache/stream.ts:12-23,162-169`), so the catch-up is normally empty.

**Can a stale cache return a wrong layout after an edit?** No, by construction: the answer set is fixed after a check that *started after the command arrived*; `Store.put` refuses any snapshot older in `layout_rev` or spark `rev` than what it holds and honours tombstone revs (`store.ts:119-156`); the stats memo is keyed by spark rev and evicted on every rev bump (`cells.ts:446-453`, `fresh.ts` `onRevBump`). The one soft spot is the fuzzy resolver on *reads* (§H #9).

| verb | network on path | compute | measured (M3, warm / cold) |
|---|---|---|---|
| `!view x` (`view.ts:21-36`) | `/v1/meta` 304 | `find` over 4.2 k names → `cells.rowFor` = harvest cell if proven else wasm (single-flight lock, `host.ts:194-209`) | 43 + 0.1 ms warm; **+709 ms** first ruled lookup per corpus (extended tables), 75–117 ms first plain lookup per corpus (`03-b6-plan.md` §2.1, §2.5) |
| `!add` (`add.ts:138-168`) | meta 304 + `POST /v1/layouts` (no If-Match: creation) + fold response + stats for reply | one wasm compute | 43 + ~50–100 ms DB + 1–20 ms compute |
| `!rename` (`rename.ts:24-36`) | meta + `GET` fresh by id (`shared.ts:346-362`) + `PATCH` with `If-Match: layout:<rev>` | none | 43 + 2 round trips (~80–120 ms) |
| `!swap!` (`cycle!.ts:35-70`) | meta + fresh GET + `PUT` with `If-Match: spark:<rev>` + fold + stats for reply | one compute | 43 + 2 RTs + compute; bench 39 ms warm / 216–726 ms when a table is cold |
| `!like` (`like.ts:36-61`) | meta + fresh GET (for the live `likes` list) + `PUT .../like`, no If-Match by design | none | 43 + 2 RTs |
| `!rank sfb` (`rank.ts:109-129`) | meta 304 | `missingCount`; if >50 → reply "Computing N layouts" and compute in background; else `allRows` (sequential `await` per record, `core/stats/stats-cache.ts allRows`) then sort | **37–45 ms** all-cached (rebuilds every row each call); **1.0–1.6 s** with 50 misses; **never ranks** above 50 (`03-b6-plan.md` §2.3) |

Bench (`bot/scripts/bench-b6.mjs`) requires `web/data`, absent in this worktree; I did not re-run it. The numbers above are the plan's, recorded 2026-09-11 on the same code paths.

## C. Rankings

- Per-layout stats for sorts are **not precomputed anywhere the bot owns**. Source order per (id, corpus, space): (1) the site's nightly harvest cell, served only if `provenance.prove()` holds (`cells.ts:288-300`, `provenance.ts:301-319`: same publish, same engine pin, same keys, same board, same applied rules, same engine path); (2) otherwise the bot's wasm, memoised per (id, spark rev, corpus-key), LRU 2 000 entries (`cells.ts:33-37`). Nothing on the volume, nothing in D1, nothing from the stats service.
- **Invalidation of one layout:** rev bump → `cells.evict(id)` drops memo + proof verdicts (`cells.ts:446-453`). The next `rank` then finds it "missing" and recomputes it inline (≤50) or refuses (>50). No eager recompute, no row table: plan §4 (S4) is **not implemented** (`grep rowTable|stale bot/src` → nothing).
- **Cold full recompute:** warm wasm 0.6–18 ms per plain cell (reddit 18 ms), 60–270 ms per ruled cell (`03-b6-plan.md` §2.1). 4 200 layouts × 1 corpus ≈ 76 s on the M3 for reddit alone; × 13 corpora × 3 spaces ≈ 50 min single-threaded, likely 2–3× slower on `shared-cpu-1x`. That is why the harvest reuse exists, and why every new publish adoption (`cells.ts:327-333` calls `cache.reset()`) or every layout edited since the last nightly build shows up as a miss.
- **Stale ordering without saying so?** No: `rank` either ranks from current cells or refuses. The failure is the opposite of R3 ("answer at once, possibly stale, say so"): it *blocks* up to 1.6 s or *refuses* ("Computing 67 layouts" was the observed state on a fresh boot against a two-day-old build, §2.3). `auto` spacegrams doubles the miss count (`cells.ts:380-383`).

## D. Write path

- Transport: Ed25519 client-lane signing on every DB call, `X-Akl-Actor` = Discord user id, `X-Client-Version`, 20 s timeout (`client/http.ts:130-199`, `client/sign.ts`). No `Authorization` ever.
- Every mutating verb except `add`/`like`/`unlike` goes through `resolveWriteTarget` (exact NOCASE name via the freshly verified cache, re-fetched by id, else by name at layoutdb; never fuzzy, `shared.ts:346-362`) → `writeWithFreshRecord` with a **scoped `If-Match`** built from the fresh record (`shared.ts:407-441`). 2xx → response folded into the store *before* the ticket settles (`main.ts:256-261`), so a same-user `!view` right after sees it. `409 stale` → the conflicting record is folded and the user gets "changed a moment ago"; **no retry loop anywhere** (`shared.ts:434`). `403/404/409 name_taken` → cmini-parity strings.
- Errors to the user: any non-2xx maps to `Error: <db message>`; a timeout is converted into `{status:0, error:'timeout'}` and reported as an error (`http.ts:152-162`); 5xx additionally DMs the operator (`http.ts:177-186`). Nothing is fire-and-forget: every write is awaited and answered.
- **Hazard (R1 "never misreported"):** if the PUT/POST commits and the response is lost (timeout at 20 s, or a 5xx after commit), the bot tells the user it failed. The SSE/next check will fold the real state, but the user was told "Error". For `swap!`/`cycle!`/`mirror!` a natural user retry then applies the transform **again on the new rev** (the fresh GET picks up the committed state, so `If-Match` passes) and *undoes* the first swap. `add` retries self-correct (409 name_taken → "already exists"). There is no idempotency key on the API and no post-timeout reconciliation read.

## E. Relationship to the site

- **Shared, via `@akl/core` (bundled at build):** `swap-engine.ts` driver + lock, `session.swapLayoutPayload`, `rules` (magic compile), `stats/stats-cache` (the harvest/memo policy, also used by the SPA's live-recompute memo), `stats/mana2` composition (`cminiRow`, `engine/compose.ts`), `mana2-partitions`, `dataorigin` paths. `@akl/layout-formats` for `spark/1`. Good: numbers come from the exact code the site uses (LDB-B5 parity test).
- **Duplicated on purpose:** `engine/worker.ts` (217 LOC) re-implements `web/swap-worker.js`'s protocol for `worker_threads`; `akl1board.ts` and `shared.ts:93-97` copy spark's board-word derivation; `scripts/gen-key.mjs`/`sign.mjs` copy `client/sign.ts`. The per-corpus n-gram table is fetched twice (raw text for the wasm, parsed JSON for `ngrams.ts`).
- **Dependence on akl.gg being up:** hard at boot (defs, build_id, wasm, the four proof files: `main.ts:399-427`), and at every first touch of a corpus (harvest, plain/extended/sg tables, n-gram tables, words). After warm-up the bot keeps answering if akl.gg goes down, except for new corpora and the hourly publish re-read (best-effort, `provenance.ts:254-268`). Should it? The dependence is on *static files* (Cloudflare Pages), which is about as available as anything here, but it couples the bot's boot and correctness to the site's *deploy timing*: `EngineSkew` fails boot if the site's `build_id.json` pin differs from the wasm it just served (only mid-deploy), and `PublishMoved` throws after 3 sandwich attempts during a site deploy (`provenance.ts:237-252`), which surfaces as a verb error. Baking the wasm + defs into the image (they are pinned by `mana2_pin` anyway) would remove the boot dependence; the stats data dependence goes away with §H #1.

## H. Top 10 risks, ranked, with fixes

1. **Stats architecture: provenance proof + publish sandwich instead of owned, persisted cells (simplicity + R3).** 5 equality conditions over 4 separately fetched files, a before/after `build_id.json` sandwich, hourly re-adoption that wipes memo/proofs/tables, and a `PublishMoved` failure mode during site deploys (`provenance.ts`, `cells.ts:327-333`). **Fix:** key cells by `hash(keys, board, resolved rules, enginePin, corpus, space)`, persist them on the `/data` volume (a few MB per table: 4 200 × 9 fields), compute eagerly on every rev bump for all 39 (corpus, space) pairs of a plain layout (138–684 ms measured) and lazily/queued for ruled ones, seed once from the site harvest if you like. Then `rank` reads a row table, the site's publish cadence stops mattering to the bot, and ~600 LOC go away.
2. **`rank` violates R3 (`rank.ts:109-113`):** blocks 1–1.6 s at ≤50 misses, refuses above 50; every akl.gg publish and every edit since the last build creates misses; `auto` doubles them. **Fix:** row table per (corpus, space) updated per rev bump, answer at once, footer for stale rows (plan §4.2–4.3; copy needs sign-off).
3. **Write misreported on lost response → retry double-applies (R1).** `http.ts:152-162` turns a 20 s timeout into "Error"; a committed PUT then looks failed, and a retried `swap!` re-swaps on the new rev. **Fix:** on timeout/5xx for a mutating call, re-GET the record and compare spark rev/payload to the intended result; if it landed, answer success. Longer term: an `Idempotency-Key` on the API.
4. **OOM: one wasm worker, tables never unloaded** (`host.ts:156-181`; bench §2.2: shai extended +481 MB, one engine 1.1–1.6 GB). A few ruled lookups across heavy corpora can kill the 1 GB machine → crash loop → dropped commands. The 192 MB V8 heap cap is a second self-inflicted ceiling. **Fix:** cap resident (corpus, space) table sets, dispose+recreate the worker to reclaim, or go to 2 GB (cheap). Q7 in the plan is still open.
5. **First command after boot pays the catch-up** (F5: 1 066 ms of a 1 822 ms `view`; `main.ts` never awaits `ensureFresh` before `client.login()` at `:692`). **Fix:** `await runtime.fresh.ensureFresh()` and pre-load the default corpus's plain+sg+extended tables before login.
6. **Cold table loads on the request path**: first ruled lookup per corpus 0.7–2 s, first plain 75–117 ms (`03-b6-plan.md` §2.1/§2.6). **Fix:** boot warm-up for `DEFAULT_CORPUS`; #1 removes most recomputes.
7. **Deploy gate depends on a live-network parity test with a stale fixture** (`numbers.test.ts:284`, red now; `bot.yml` test → deploy). Deploys can be blocked or flake on the site's data, not the bot's code. **Fix:** move LDB-B5 to a nightly/manual workflow, gate deploys on offline tests only.
8. **Single machine, hard boot dependence on akl.gg + layoutdb + Discord, silent drops during restart** (§A). Two gateway instances aren't an option without sharding, so **fix** by shrinking boot: bake wasm+defs into the image, persist the dump/cells on the volume and boot from them, then catch up; treat akl.gg fetches as refresh, not prerequisite.
9. **Fuzzy `find` on read verbs answers a different layout with no marker** (F8; `view.ts:21`, `render/find.ts`). "Incorrect information" under R1's wording for a just-deleted exact name. **Fix:** exact/prefix first; label a fuzzy hit ("showing `x`; did you mean…") or refuse for exact-looking misses. saltorbit's call (cmini parity).
10. **Operator visibility only via Discord DMs** (`alerts.ts`, `watchdog.ts`): if Discord is the failing component nothing alerts; the hourly `alerts snapshot` log line is the only non-Discord signal. Low severity. **Fix:** Fly log-based alert on `slow command`/`db_unreachable` lines, or accept.

Not risks: the replica fold is rev-guarded and replay-equivalent (LDB-B65/B70 tests), the 304 check is live against D1, writes always carry scoped `If-Match`, mentions are neutralised, replies are capped.

## Verdict

**Keep the architecture; do not restructure into a thin client.** The bot already holds the full replica (4.2 k records ≈ 21 MB RSS, `README.md:889-897`) fed by dump + `/v1/changes` + SSE, and verifies it per command with a 43 ms conditional GET. That is the simplest way to meet R1 and R2 for lookups, and it works: after the F7 fix the write path resolves exact names against a verified cache and writes with `If-Match`. A "bot as thin client of a shared stats/query service" would add a network hop to every command, a second freshness protocol, and inherit the stats service's cadence (30 s ticks, ~8 min per ruled layout on `shared-cpu-2x`, `02-handoff.md` A3), which cannot meet R2/R3. The stats service should stay what it is: the SPA's bulk publisher.

What to change is *where the bot's stats live*: replace the site-harvest borrowing (provenance + publish tracker + adoption resets) with a content-hash-keyed cell cache on the volume, computed eagerly on rev bumps and read by a row table, so `rank` never blocks and site deploys stop invalidating the bot. Cost: ~40 MB more RSS for 39 resident row tables (or keep 3 corpora resident and the rest on disk), a few MB of volume, and one background compute per edit (0.1–0.7 s plain, seconds for ruled). Alongside: warm `ensureFresh` and the default corpus before login, reconcile writes after a lost response, bound wasm table residency, and take the live parity test off the deploy gate. Costs stay at one 1–2 GB Fly machine plus a volume.
