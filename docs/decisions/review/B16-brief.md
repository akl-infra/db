# B16 — grouped compute in the publisher (implementation brief, scouted 2026-09-13)

Goal (saltorbit): a full rebuild through the publisher must not take 12 h. Today the publisher spends ≈ 3 s per layout, ~90 % of it re-parsing corpora, because every layout is its own `fast_sync_patch.py` run.

## Today
- `bot/src/publisher/compute.ts:149-208` `computeLayoutCells()` — ONE layout per process. Writes `<workDir>/<id>-<pid>-<ts>/data-root/layouts/<id>.json` (+ `rules.json`), spawns `MANA2_CLI [...MANA2_CLI_ARGS] --layout <id> --out <path> --data-root <dir> [--rules-file] [--corpora <csv>] --jobs <n>`, reads ONLY the `--out` JSON (`{schema:2, layout, rules_sig, mana2:{...}}`). Called from `index.ts:397` (`computeOne`) inside a `publisherCliConcurrency`-wide pool (default 1) in `publishOneTick` (`index.ts:472-487`).
- `scripts/fast_sync_patch.py` `run(layout_id, …)` (`:168`; argparse `--layout` singular `:331`): 6 `mana2bridge layouts[-magic]` conversions per layout (one per (board,space) context, `:80-110`); one workdir per `(corpus, spacegrams)` group (`build_group_workdir`, `:268-275`, 2C groups); one `mana2bridge harvest` subprocess per group via `ThreadPoolExecutor(max_workers=jobs)` (`:147-165`, `:278-283`), ids fed via `harvest_ids.txt` (`:141-143`). All results `.update()`d into one in-memory dict, single `json.dump` at the end (`:277-294`). So per layout: 2C subprocesses and 2C corpus parses.
- CI full harvest (`scripts/build_mana2.py:432-529`, `run()` `:570`): ONE `mana2bridge harvest` per (board,space,corpus) group fed the ENTIRE live ids file; Go-side batches (`harvest.go`, 128-id floor, `small_batch` for magic groups); `--jobs` = cpu_count; `full-rebuild.yml` matrixes by corpus across runners.
- Output re-keying: `index.ts:406-414` → `cellKeyFor({keys, board, ruleSet, enginePin, corpus, space})` (`bot/src/cache/cellkey.ts:66-79`) — the cell key never encodes the layout id, so a grouped result can be split per layout by the `<id>@<board>.<space>` prefix `fast_sync_patch.py` already uses to demux magic groups (`:138-160`). No hash change.
- Knobs: `PUBLISHER_TICK_MAX_LAYOUTS` (config.ts:279, default 25; bounds ids/tick at `index.ts:645`), `PUBLISHER_CLI_JOBS` (config.ts:280, default 2 → `--jobs`), `PUBLISHER_CLI_CONCURRENCY` (config.ts:268, default 1; the worker pool), `MANA2_CLI_ARGS` (config.ts:266).

## Minimal change
1. `fast_sync_patch.py`: accept `--layouts <file|csv>` (plural; keep `--layout`), thread the list through `convert_layout_per_context` / `build_group_workdir` / `harvest_group`, naming entries `<id>@<board>.<space>`; the tick's N layouts then share the 2C group subprocesses (2C corpus parses per TICK instead of per layout).
2. `compute.ts`: `computeLayoutsCells(batch)` — write N layout files under one `data-root`, call the CLI once, split the single `--out` patch by `<id>@` prefix, then the existing per-cell `cellKeyFor` re-keying. `computeOne` in `index.ts` becomes a batch step ahead of the worker loop (or the loop collapses to one batch).
3. Tick size scales with the backlog: a handful for a live edit (freshness), hundreds during a pass, ceiling `PUBLISHER_TICK_MAX_LAYOUTS` (raise the default once RSS is measured); the `mana2_cells` dict and per-group `.jsonc` staging grow linearly with the tick, so the ceiling IS the memory knob (machine 2 GB, bot ≈ 550 MB). Measure peak RSS of one grouped run at 100/300/500 layouts before picking the default.
4. Child at low OS priority (B15, may already be in B12).
5. Keep `PUBLISHER_CLI_CONCURRENCY` effectively 1: `build_group_workdir` rmtree/rebuilds the SHARED `build/fastsyncwork/group-*` dirs (latent race if two `fast_sync_patch.py` run concurrently — B8 note). Grouping makes one subprocess-in-flight per tick natural; if concurrency is ever raised, make `workdir` per-run-unique first.

## Expected
Per tick: 2C CLI subprocesses regardless of N → a 500-layout tick costs ≈ (2C parses) + (500 × per-layout harvest, ~0.1–0.3 s) instead of 500 × 3.3 s. Full 4,178-layout pass ≈ 1.5–2 h on 1 vCPU (≈ 1 h on performance-2x). Invariants to register: grouped output ≡ per-layout output cell-for-cell (oracle test over ≥ 3 layouts incl. one magic); tick size never exceeds the ceiling; a failing layout inside a batch fails only that layout (retried next tick), never the whole batch.
